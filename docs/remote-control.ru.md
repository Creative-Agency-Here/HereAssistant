# Удалённое управление (`/rc`)

English version: [remote-control.md](remote-control.md)

`/rc` публикует текущую живую сессию терминального чата (`chat.py`), после чего
её можно наблюдать, а при разрешении политикой проекта — ещё и вести из браузера
вместо ввода в терминале. По умолчанию режим выключен для любого проекта и
остаётся выключенным, пока владелец явно не включит его.

## Текущий статус реализации

Прочитай это, прежде чем полагаться на `/rc`:

- **Что работает локально без сети:** `/rc`, `/rc status`, `/rc off`, `/rc stop`,
  гейты приватности и единая очередь-арбитр локального и удалённого ввода.
  Публикация без настроенного control-plane пишет строку в локальную таблицу
  `rc_publications` и не делает ни одного сетевого запроса.
- **Что подключено к сети:** при одновременно заданных базовом URL control-plane
  и credential устройства терминальный чат создаёт клиента, забирает команды,
  исполняет их (`prompt`, `stop`, `git_preflight`, `git_commit`, `git_push`,
  `approval_decision`) и фоном сливает очередь событий. Пустой URL либо
  отсутствие credential означает, что режим выключен целиком.
- **Что готово со стороны браузера:** `webapp/api/routes/remote_control.py` —
  прокси, через который авторизованная сессия WebApp листает публикации и ставит
  команды; интерфейс — `webapp/front/components/remote-control/` и
  `webapp/front/composables/useRemoteControl.ts`.
- **Чего в этом репозитории нет:** самого control-plane сервера. HereAssistant —
  сторона устройства и браузера; сервер, реализующий описанный здесь контракт,
  поставляется отдельно.
- **Что сознательно не подключено:** потоковая передача ответа по кускам
  (`emit_progress`) и событие запроса подтверждения (`emit_approval_required`) —
  ни один поддерживаемый провайдер не запрашивает подтверждение инструмента в
  реальном времени, поэтому источника таких событий на устройстве нет. Команда
  `approval_decision` по этой причине всегда отвечает отказом, а не согласием.

## Команды

| Команда | Алиасы | Эффект |
|---|---|---|
| `/rc` | `/rc on`, `/rc publish` | Публикует текущую сессию (если разрешает политика). Повторный вызов при активной публикации — no-op. |
| `/rc status` | `/rc st` | Показывает состояние публикации, режим приватности, устройство и локальную очередь исполнения. |
| `/rc stop` | — | Останавливает текущий выполняющийся запуск. Очередь не трогает. |
| `/rc off` | `/rc close` | Немедленно снимает публикацию и очищает очередь. |

Пока публикация активна, смена провайдера, аккаунта, модели, рабочей папки
или самой сессии (`/model`, `/account`, `/cwd`, `/new`, `/resume`, `/user`)
заблокирована — сначала нужно `/rc off` (`CommandRouter._rc_blocked` в
`chat_commands.py`).

## Локальный и удалённый ввод: один писатель, одна очередь

`RemoteControlCoordinator` — единственный писатель в CLI провайдера для этой
сессии:

- ровно один запуск провайдера одновременно, сериализация через `asyncio.Lock`;
- текущий выполняющийся запуск **никогда не вытесняется** — новый ввод,
  локальный или удалённый, встаёт в очередь FIFO в памяти;
- порядок — по моменту принятия ввода; при равенстве побеждает локальный ввод
  (`_SOURCE_RANK = {"local": 0, "remote": 1}`);
- удалённый prompt никогда не меняет провайдера, аккаунт, модель, рабочую
  папку или режим разрешений — это просто строка prompt, идущая тем же путём
  `_run_prompt`, что и локальный ввод.

`/rc status` печатает источник выполняющегося элемента и для каждого элемента
очереди — его источник и первые 60 символов текста.

## Транспортная модель (клиентская сторона)

Устройство никогда не открывает входящий порт — все его соединения исходящие.

- **Источник истины — HTTPS.** Ожидающие команды забираются
  `POST rc/commands/claim` (`device_id`, `last_sequence`); результаты и смены
  статуса отправляются `POST rc/events`; живость подтверждается
  `POST rc/heartbeat`.
- **WebSocket — только уведомление.** `WakeupListener` подключается через
  `python-socketio` (опциональная зависимость: её отсутствие означает лишь,
  что клиент работает исключительно на HTTPS-реконсиляции) и слушает одно
  событие — `rc:command:available`. Его получение только досрочно запускает
  HTTPS-реконсиляцию; потеря WebSocket-соединения никогда не теряет команду,
  потому что её всё равно заберёт очередной плановый HTTPS-реконсиль.
- **Периодичность.** Сетевой цикл координатора реконсилирует и шлёт heartbeat
  вместе примерно раз в `HEARTBEAT_INTERVAL_SEC` = 15 секунд
  (`core/remote_control/config.py`). Публикация считается offline после
  `OFFLINE_AFTER_SEC` = 45 секунд без heartbeat (три пропущенных цикла).
- **Базовый URL.** `RC_CONTROL_PLANE_URL` читается один раз, обязан быть
  абсолютным `https://` URL и по умолчанию пуст. Пустое значение означает, что
  режим выключен целиком — ни один запрос никогда не отправляется.
- **Ошибки нормализуются.** `ControlPlaneClient` никогда не отдаёт тело
  ответа наружу: `401`/`403` превращается в `rc_unauthorized`, любой другой
  `>=400` или сетевой сбой — в `rc_unavailable`, не-JSON тело — в
  `rc_invalid_response`. Неудачный claim или heartbeat лишь пишет
  warning в лог и повторяется на следующем цикле — локальную сессию это
  никогда не роняет.

## Приватность: default deny

Единственная точка решений — `core/project_config.py`. Каждый гейт ниже
возвращает `False`, пока `.hereassistant/project.yml` проекта явно не
разрешит обратное (полный формат политики — в [privacy.md](privacy.md)).
Глобального переключателя нет — приватность ослабляется только на уровне
конкретного проекта.

| Гейт | Функция | Что требуется | Что открывает |
|---|---|---|---|
| Presence | `can_publish_rc_presence` | `remote_control.enabled: true` **и** либо `mode: crm` + `sync.enabled: true`, либо `mode: private` + `remote_control.allow_presence_in_private: true` | `/rc` вообще срабатывает; наружу становятся видны opaque id публикации, имя/тип устройства, состояние, срок действия и флаги возможностей ниже. `mode: local` никогда не публикует presence. |
| Удалённые prompt | `can_receive_remote_prompts` | активный CRM-канал (`mode: crm` + `sync.enabled: true` + `remote_control.enabled: true`) **и** `sync.send_prompts: true` | Команда с control-plane может выполниться как prompt на этом устройстве (это канал удалённого выполнения кода — см. «Ограничения»). |
| Стриминг сообщений | `can_stream_rc_messages` | активный CRM-канал **и** `sync.send_messages: true` | Могут отправляться текст ответа ассистента (обрезан до 800 символов, домашний путь заменён на `~`) и события вызова инструментов. |
| Стриминг диффов | `can_stream_rc_diffs` | активный CRM-канал **и** `sync.send_diffs: true` | Могут отправляться сводки правок (изменённые файлы / добавления / удаления и до 50 относительных путей). Содержимого самого диффа в этом payload никогда нет. |
| Метаданные коммита | `can_stream_rc_commits` | активный CRM-канал **и** `sync.send_commits: true` | SHA и сообщение коммита могут прикрепляться к событию `rc.command_status`. |
| Удалённые Git-действия | `can_execute_rc_git` | активный CRM-канал (`mode: crm` + `sync.enabled: true` + `remote_control.enabled: true`) | На этом устройстве могут выполниться `git_preflight` / `git_commit` / `git_push` (см. ниже). Стриминг этих метаданных наружу регулируется отдельным гейтом `can_stream_rc_commits`. |

«Активный CRM-канал» (`_rc_crm_active`) всегда означает одновременно
`mode: crm`, `sync.enabled: true` и `remote_control.enabled: true` — проект
`private` или `local` никогда не проходит ни один гейт дальше presence.

### Что может отдать приватный проект

Проект `private` с `remote_control.enabled: true` и
`remote_control.allow_presence_in_private: true` публикует presence — и
ничего сверх этого. `publications.presence_payload` в этом случае содержит
только: opaque id публикации, `privacyMode: "private"`, id/имя/тип
устройства, состояние, generation, срок действия и карту возможностей, где
всё — `false`. Рабочей папки, имени проекта, repo или id сессии провайдера в
нём нет никогда. Даже единственный тип события, который приватный проект
может отправить, — `events.emit_command_status`, — несёт только id команды и
статус (`queued`/`running`/`succeeded`/`failed`/…), никогда текст, пути или
метаданные коммита: для них нужен отдельный гейт `can_stream_rc_commits`,
которому приватный проект никогда не удовлетворяет.

Любой исходящий payload дополнительно проходит фиксированную очистку
(`core/remote_control/events.py`): домашний путь заменяется на `~`, текстовые
поля обрезаются (800 символов для сообщений, 200 — для коротких полей) с
пометкой `…[обрезано]`, имена инструментов сводятся к безопасным символам, а
любой путь вне корня проекта (включая всё под домашней папкой) не
отправляется вовсе, а отбрасывается.

## Настройка

| Параметр | Где | По умолчанию | Эффект |
|---|---|---|---|
| `RC_CONTROL_PLANE_URL` | окружение | пусто | Базовый URL, который использовал бы `ControlPlaneClient`/`WakeupListener` устройства. Пусто = режим выключен. Чтобы считаться настроенным, обязан быть абсолютным `https://` URL. |
| `RC_PROXY_CRM_BASE_URL` | окружение (процесс WebApp API) | не задан | Базовый URL, который вызывает серверный браузерный прокси WebApp. Не задан/не-https = маршруты `/api/rc/*` отвечают `rc_not_configured` (503) без единого исходящего запроса. |
| `RC_PROXY_CRM_TOKEN` | окружение (процесс WebApp API) | не задан | Серверный bearer-токен для прокси выше. Браузеру никогда не отдаётся. |
| `remote_control.enabled` | `.hereassistant/project.yml` | `false` | Главный переключатель для проекта; с него начинается каждый гейт выше. |
| `remote_control.allow_presence_in_private` | `.hereassistant/project.yml` | `false` | Имеет смысл только для `mode: private`; позволяет такому проекту публиковать только presence, без единой возможности. |
| `remote_control.ttl_minutes` | `.hereassistant/project.yml` | `120` | Ограничен диапазоном 5–480 минут; используется для расчёта `expiresAt` публикации. |

Ни у одной из трёх переменных окружения нет домена по умолчанию, зашитого в
код или в `.env.example`, — каждое развёртывание задаёт своё значение.

### Device credential

`core/remote_control/credential_store.py` определяет, где хранился бы
control-plane credential устройства, если бы что-то его создавало:

- macOS: запись в Keychain через `security` (сервис `HereAssistant Remote
  Control`, аккаунт `device-credential`).
- Везде остальное: JSON-файл
  `<runtime>/state/remote_control/device_credential.json` с правами `0600`
  (при первой записи в лог пишется одноразовое предупреждение, что это
  менее безопасно, чем системное хранилище секретов).
- Сырой credential никогда не попадает в SQLite, `.env` или `project.yml` — в
  лог может попасть только факт его наличия/отсутствия.
- Чтобы отозвать устройство: удали его credential из того хранилища, где он
  лежит (`security delete-generic-password` на macOS либо удаление JSON-файла)
  и отзови его на стороне control-plane, чтобы устаревший токен нельзя было
  переиспользовать.

Как уже отмечено выше, ничто в этом репозитории сегодня не вызывает
`default_store()` вне собственных тестов — подкоманды `/rc`, которая бы
создавала, показывала или ротировала device credential, пока нет.

## Git-действия

`core/remote_control/git_actions.py` исполняет небольшой набор **типизированных
intent**, никогда не shell-команду. Каждое действие:

1. Отклоняется сразу, если `can_execute_rc_git` для политики проекта не
   `true`.
2. Разрешает целевую директорию только через
   `project_config.project_root_for` — доверенный корень, явно настроенный в
   `project.yml`, никогда не угадываемый и не произвольный путь.
3. Выполняет Git через существующий `core.git_projects.run_git`, который
   проводит credential через credential-helper proxy и vault broker: сырой
   Git credential никогда не появляется в Python-коде, результате, логах или
   payload команды, а весь вывод Git санитизируется перед повторным
   использованием.

| Действие | Что делает | Особенности |
|---|---|---|
| `git_preflight` | Только чтение: разрешает и проверяет URL remote и grant, читает текущую ветку, `git status --porcelain`, ahead/behind относительно upstream, и делает read-only `ls-remote`, чтобы подтвердить доступность broker/remote. | Никогда не меняет рабочее дерево. |
| `git_commit` | Индексирует **только явно перечисленные пути** (`git add -- <paths...>`) и коммитит с заданным сообщением. | `git add .`, `-A`, `-u`, глобы, абсолютные пути и `..` отклоняются ещё до запуска любой Git-команды — запросить массовое добавление невозможно. |
| `git_push` | Проверяет имя remote, подтверждает write-grant именно на этот URL remote, сначала выполняет `git push --dry-run`, и только затем — реальный push, ровно один раз. | Dry-run ловит non-fast-forward и подобные сбои ещё до того, как что-либо реально запушено. |

### Коды ошибок

`RcGitErrorCode` — фиксированный, не расширяемый набор:

- `AUTH_REQUIRED` — grant на репозиторий требует (пере)авторизации.
- `REMOTE_DENIED` — этот remote/репозиторий не входит в список разрешённых
  этому пользователю для записи.
- `PREFLIGHT_FAILED` — само действие некорректно (недоверенный корень,
  запрещённые пути, пустое сообщение коммита, обычная ошибка Git до/без
  попытки push) либо гейт приватности запретил его.
- `UNKNOWN_RECONCILE_REQUIRED` — возвращает **только** `git_push`, и только
  когда реальный вызов push падает с сетевой/транспортной ошибкой *после*
  того, как dry-run уже прошёл успешно. В этот момент неизвестно, дошёл ли
  push до remote, поэтому `git_push` не повторяет попытку автоматически: он
  делает read-only `ls-remote HEAD` и возвращает эту ссылку вместе с ошибкой,
  чтобы вызывающая сторона сверила состояние вручную перед повтором.

## Ограничения и границы безопасности

- **Это канал удалённого выполнения кода по своей сути.** Любой prompt,
  принятый через `can_receive_remote_prompts`, выполняется с теми же правами,
  что и prompt, набранный локально в терминале.
- `CLAUDE_PERMISSION_MODE=bypassPermissions` запрещён во всём проекте (см.
  `CLAUDE.md` репозитория) именно потому, что превратил бы prompt-injection в
  бесконтрольный доступ к shell/файлам; `/rc` эту политику не меняет и не
  обходит — удалённый prompt подчиняется тому же режиму разрешений, что и
  локальный.
- **Произвольного shell-канала нет.** `rc_command_receipts.claim` принимает
  только фиксированный набор типов команд — `prompt`, `stop`,
  `approval_decision`, `git_preflight`, `git_commit`, `git_push` — и
  отклоняет (`unknown_command_type`) всё остальное ещё до какого-либо
  исполнения. Браузерный прокси сужает этот набор ещё сильнее: сессии
  браузера позволено создавать только `prompt`, `stop`, `git_commit` или
  `git_push` (`approval_decision` и `git_preflight` — служебные сигналы
  раннера, из браузера они не создаются).
- **Повторная доставка не может вызвать повторное исполнение.** Receipt
  команды записывается *до* начала исполнения, по ключу id команды. Повторная
  доставка того же id команды с тем же payload hash — no-op; повторная
  доставка с *другим* payload hash отклоняется сразу
  (`payload_hash_mismatch`) — fail closed вместо тихого исполнения
  изменённой команды под старым id.
