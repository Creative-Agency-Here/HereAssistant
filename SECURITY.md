# Security Policy

## Модель угроз: это шлюз удалённого выполнения кода

HereAssistant по замыслу — мост «Telegram → CLI-агент (claude/codex/gemini/qwen) на
твоей машине». Агент читает и правит файлы, запускает команды. Любой, кто
получил доступ к боту, получает возможности агента на хосте. Относись к
развёртыванию соответственно.

## Критические точки

- **Доступ к Telegram-боту.** `ADMIN_IDS` — единственный список допущенных.
  Токен бота (`TELEGRAM_BOT_TOKEN`) = возможность перехватить управление.
- **Auth-файлы провайдеров.** `.runtime/cli_homes/<аккаунт>/` содержит
  OAuth-креды и API-ключи планов Claude/OpenAI/Google/Alibaba. Не копируй, не коммить, бэкапь
  только шифрованно.
- **`WEBAPP_ACCESS_KEY`.** Полный доступ владельца к WebApp из браузера без
  Telegram. Генерируй длинный случайный (`openssl rand -hex 32`), не логируй,
  не вставляй в URL при передаче другим людям.
- **`WEBAPP_DEV_SKIP_AUTH=1` в проде ЗАПРЕЩЁН** — это полное отключение
  авторизации WebApp.
- **`SERVICE_API_TOKEN`.** Даёт внешней системе доступ к `/api/v1/*`, но не
  обходит privacy-политику проектов (private/local невидимы). Пустой токен =
  API отключён.
- **История и журналы.** Если проект разрешил хранение
  (`.hereassistant/project.yml`), в `bridge.sqlite3` и `.runtime/logs/`
  оказываются prompt'ы, ответы и диффы — там могут быть секреты. По умолчанию
  хранение выключено (см. `docs/privacy.md`).
- **Права CLI.** `CLAUDE_PERMISSION_MODE=bypassPermissions` не используем:
  авто-одобрение Bash/Write превращает любой prompt-injection в RCE.
  Для Qwen по той же причине запрещён `QWEN_APPROVAL_MODE=yolo`; дефолт —
  classifier-driven `auto`.

## Монитор разрушительных команд — это не защита

`core/command_risk.py` оценивает shell-вызовы агента по радиусу поражения и при
уровне `CONFIRM` и выше присылает предупреждение в чат. **Это наблюдение, а не
контроль:**

- команду исполняет сам CLI-агент в своём процессе, шлюз её не останавливает —
  предупреждение приходит в момент вызова, а не до него;
- классификатор лексический, его обходит любая динамика: `base64 -d | sh`,
  `python -c`, сборка строки в переменной;
- у провайдера Codex монитор не работает вовсе — он не стримит события;
- на Windows правила bash к `cmd`/PowerShell не применяются.

Реальные границы дают уровни ниже: sandbox-профили Codex через `/permissions`,
OS-runner с отдельным Unix-пользователем и права ФС. Монитор существует, чтобы
человек быстрее заметил происходящее, и не должен создавать ложного спокойствия.

### Что даёт PreToolUse-хук Claude Code (проверено 2026-07-29)

Документация Anthropic об этом молчит, поэтому проверено зондом на живой системе:

- хук **работает** в headless-режиме (`claude --print --output-format stream-json`)
  и действительно останавливает вызов;
- ответ `{"hookSpecificOutput": {"permissionDecision": "deny", ...}}` с кодом 0
  блокирует инструмент; блокировка **видна снаружи** — в потоке приходит
  `tool_result` с `is_error: true`, а его содержимое равно тексту причины;
- хук получает полный ввод инструмента: `tool_input.command` целиком, плюс `cwd`,
  `session_id`, `permission_mode` и путь к транскрипту;
- **при таймауте хука команда выполняется** (fail-open). Проверено: хук со
  `sleep 8` при `timeout: 2` не остановил `touch`. У Qwen Code документировано
  строже: решение `"ask"` в headless-режиме падает до `"deny"`.

Последнее определяет дизайн: **ждать решения человека внутри хука нельзя** — пока
человек читает Telegram, таймаут откроет проход. Блокировать хуком допустимо
только по мгновенному локальному вердикту, без сети и без ожидания ответа.

### Что блокируется на самом деле

`scripts/claude_risk_hook.py` подключается к профилю аккаунта при логине
(`core/risk_hook.py`, Claude и Qwen) и отклоняет **только** уровень `CATASTROPHIC`: системные
корни, `$HOME`, `~/.ssh` и прочие хранилища ключей, запись в устройства. Уровень
`CONFIRM` намеренно проходит — ложная блокировка обычной работы дороже, чем
предупреждение, которое и так приходит в чат.

Проверено на живом headless-запуске: команда не выполняется, а пользователь
видит причину отказа. Отключается переменной `HEREASSISTANT_RISK_HOOK=0`.

Границы этой блокировки:

- **Claude Code и Qwen Code.** Контракт ответа у них совпадает
  (`hookSpecificOutput.permissionDecision: "deny"`), поэтому работает один скрипт.
  У Gemini и Codex механизма нет вовсе — там остаётся только монитор.
  Важное различие: у Claude таймаут хука задаётся в **секундах**, у Qwen — в
  **миллисекундах** (умолчание 60000). Одинаковое число означало бы у Qwen
  десять миллисекунд и молча неработающую защиту;
- **обходится чужим интерпретатором и рантайм-сборкой строки.** Что именно
  проходит незамеченным — зафиксировано тестами в
  `tests/core/test_command_risk_limits.py`: `base64 -d | sh`, `python3 -c`,
  `perl -e system(...)`, `eval "$(...)"`. Признак общий: лексический анализ не
  выполняет код. Закрыть это может только песочница уровня ОС;
- в том же файле стоит счётчик незамеченных приёмов — если он вырастет, тест
  покраснеет и напомнит, что защита деградировала;
- не действует на Windows-оболочки;
- **путь к хуку обязан быть экранирован.** Проверено: без кавычек в пути с
  пробелами (`.../Visual Studio Code/...`) Claude молча не запускает хук, и
  защиты просто нет — ни ошибки, ни признака.

## Рекомендации по развёртыванию

- API слушает только `127.0.0.1`; наружу — nginx с HTTPS.
- Отдельный системный пользователь без sudo; секреты — только в `.env` (0600).
- Обновляй зависимости (`pip`, `npm audit`) и следи за релизами CLI-провайдеров.

## Границы доверия

Раздельные Unix users для provider и Git runners ограничивают прямой доступ
скомпрометированного агента к другому пользователю. Это не делает HereAssistant
Core недоверенным: Core выбирает prompt, запускает runners и управляет прикладной
SQLite. Компрометированный Core может действовать от имени каждого подключённого
пользователя через штатные runner-интерфейсы.

Host root находится выше всех локальных границ и может читать память, менять
бинарники, конфигурацию и права любого процесса. `chmod`, systemd sandbox и
контейнеры уменьшают blast radius приложений, но не защищают от владельца одного
и того же хоста. Для независимых root-доменов нужны отдельные VM или серверы.

Coding agent и его tool subprocesses внутри одного runner UID составляют общий
домен доверия. Секрет, доступный этому UID, потенциально может быть прочитан и
отправлен через разрешённый provider endpoint. Поэтому Git credentials вынесены
в отдельный broker UID, а provider credentials требуют дополнительного broker/VM
слоя, если их нужно защищать и от самого provider-процесса.

Пошаговый rollout, rollback и критерии проверки описаны в
[`docs/control-plane-hardening-plan.md`](docs/control-plane-hardening-plan.md).
